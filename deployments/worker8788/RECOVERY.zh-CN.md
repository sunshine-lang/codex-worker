# 检查点恢复与供应商兼容

## 已保存进度

`project-session-state.json` 保存任务/Job/原始计划绑定、译文、版本、自检版本和项目笔记。有效工具调用后持久化，Windows 原子保存仅对短暂共享冲突做有限重试。无效检查点不会被清空或覆盖。

单内可以按内容选择翻译顺序。恢复时校验行 ID、译文、版本、任务绑定和文件指纹，模型会重新读取当前资料和规则检查。正常模型轮次提前结束由控制器在同一会话续行。

## 服务中断后的自动续翻

服务启动时核实上次执行的 Windows 进程已退出，并将核对结果绑定到原 Job 的启动时间和进程身份。具名项目有后单在等时，调度器检查其前单。确认前单因服务重启或关闭中断后，8788 使用原任务号、原 Job、原对话和草稿继续。已经在交付检查阶段的有效结果先走交付检查。原稿、对话或检查点无法核对时，后单保留原位，前单状态会显示处理原因。

人工停止会在中断执行前写进订单，优先于自动恢复。译员可以用原任务号手动恢复，或在原位补交新稿。

## 显式恢复

8788 具名项目的日常恢复可在服务运行时通过 Langflow 或整单 API 发起。排队时停止的订单沿用自己的位置和任务号。执行时停止或失败的订单会校验已保存的原稿、对话及检查点。补交新稿时指定原任务号，后单将等待新版交付。详见[整单接口](source/docs/WHOLE_TASK_API.md)。只剩此类等待订单时，也可使用 8788 桌面正常停止和启动服务。

维护人员也可以在服务空闲且模型配置与原任务一致时使用旧的离线恢复命令。

```powershell
python -m codex_remote_worker.project_recovery --config C:\CodexRemoteWorker-AppServer-8788\config.trial.json --task-id task_REPLACE_WITH_FAILED_TASK_ID
```

命令先备份旧记录及执行材料，校验原输入和检查点，再将任务重排；命令本身不调用模型。存在其他未完成任务、绑定不一致或模型配置已变化时拒绝恢复。切换供应商后不能直接将旧任务当作原配置继续。

8788 纯文本翻译由宿主随单提供指南。恢复原会话时传入 `project_doc_max_bytes=0`，避免恢复接口为读取本地项目说明而初始化 Windows 文件沙箱。每个模型轮次保持 `environments=[]`、`runtimeWorkspaceRoots=[]` 和 `translation` 权限。旧轮次用量通知可以在恢复后延迟到达，宿主只将当前轮次的统计、工具操作和译文记入本单。

8788 根据 `source_file.project_name` 持久绑定项目，同名续单和显式使用兼容编号的续单都必须找回原工作目录及原对话。恢复失败会留下错误，后单可从状态中的 `waiting_on_status_path` 查看前单。对于未绑定项目编号的旧订单，单内检查点恢复继续兼容原有兜底行为，仅对已知的、模型启动前的 Windows 配置服务错误允许新建受限会话，并记录 `history_restored=false`。

## 官方订阅与第三方供应商

桌面控制器从当前用户 Codex 配置、认证和可用模型目录读取供应商信息，不读取 cc-switch 数据库。应用设置时同步至 8788 的专用 Codex home；运行任务不直接使用个人 Codex home。设置变更仅允许在服务空闲时进行，失败回滚原配置。

官方订阅使用 ChatGPT 登录状态。第三方供应商须支持 Responses 和项目所需工具调用；OpenRouter 目录用于筛选可用工具模型，不凭通用 reasoning 支持猜测所有思考等级。

项目会话不发送最终状态 `outputSchema`，避免已观察到的第三方接口直接生成状态而跳过工具的组合问题。译文结构和完成条件仍由 Worker 校验。完整工具结果不再重复写入 App Server INFO 正文日志，大消息回传保留独立传输容量检查。

上下文覆盖保存在 8788 专用 `config.toml`。桌面“应用”操作会重新生成服务配置，之后应重新核对这些覆盖值；需要恢复本次 872,000 / 784,800 设置时，可在空闲状态运行仓库的 `tools/set_worker8788_context.py`。
