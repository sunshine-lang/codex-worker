## 0.2.1：Windows 交付检查修复

本轮读取的实际记录为任务 `job_8581d58ce38d4cfc938a5fdf278c80da`：`exit_code=0`、`turn_completed=true`、`trace_complete=true`、`stderr.log` 为空、QA 未生成。Trace 记录 128 行 CSV 生成成功，文件大小 58945 字节；这不代替宿主校验或人工审校。

发现 `files.verify_result` 未指定编码读取 UTF-8 `source.json`。对原 Siemens 工作簿生成的快照分别以 CP936、CP1252 解码均产生 `UnicodeDecodeError`，UTF-8 正常。新增测试在真实 Worker 交付调用路径模拟 Windows 默认编码：修复前复现完全相同的通用 `EXECUTION_FAILED`，修复后通过。旧服务器没有保存 Python 异常栈，因此该缺陷与此次失败一致，但需服务器重检才能最终确认。

- `source.json` 和自检 JSON 明确以 UTF-8 读取。
- 宿主意外异常记录阶段、异常类型、代码位置、编码和 OS 错误码；不记录异常原文、局部变量或凭据。
- `recheck` 只允许恢复 Codex 已正常完成、宿主检查/发布失败的任务；要求 Worker 停止并确认旧进程停止。保持原任务号、执行时间和历史错误，重新执行全部结构与安全检查，不调用模型。
- 回归覆盖中文快照、诊断脱敏、超过原执行时限后的独立补检、输入被篡改时拒绝发布、缺少正常完成证据时拒绝恢复，以及服务运行中拒绝补检。

本轮完整测试 **81 项通过，2 项 Windows 专用测试跳过**。尚未部署 0.2.1 到目标 Windows，也未重新运行模型；原任务 CSV 仍需在 Windows 上通过恢复命令读取和检查。

## 已知限制

1. Windows 服务宿主、账户权限、沙箱和进程树实现尚未在目标设备验收。`doctor --verify-sandbox` 是运行前的必要检查，不是当前已经通过的结果。
2. 这仍是单租户、一个可信 Langflow 调用方的首版；一个任务目录不等同于完整多租户隔离。
3. 自动检查主要验证结构、覆盖和明确规则，不能证明技术含义和中文质量。`needs_review` 需要人工判断。
4. 首版不自动重跑中断任务、不自动清理历史文件。运维需处理保留和磁盘容量。
5. Langflow 界面可能限制同一流程重复运行；可将本次等待设为 0，先取任务号再查询。节点本身只在引用写入时持锁，支持另一请求查询或取消。
6. 接口与模型是否可用，以实际环境与模型试跑为准；没有 Trace 逐步一致或性能 SLA 的承诺。
